 
 CarPlay 车载互联逆向工程与复刻资料 
 CarPlay 车载互联：高德导航 Hook 与画中画（PiP）逆向工程资料
 包名 com.leting · Xposed 模块 API 102 · APK v21 · 复刻用途
 该软件以 Xposed（LSPosed）钩子 侵入高德地图与系统 SystemUI，拿走高德 3D 导航的全部实时数据，注入车机主程序后以 悬浮窗卡片 与系统 画中画（PiP） 两种形态呈现；同时充当车机桌面与投屏宿主。本文按"逆向分析 + Java 语义还原骨架"两条线整理出 hook 高德地图、实现画中画、导航卡片渲染、广播接收缓存、一键导航的完整实现链与关键代码位置，供重新开发复刻时对照落地。
 1 软件总览与模块地图
 主包为 com.leting ，同时扮演 Xposed 模块、车机桌面（Launcher）、悬浮投屏宿主三个角色。反编译 APK（carplay_v21.apk）的 smali 顶层目录清晰地反映了六大模块： carplay （导航数据与浮层）、 xposed （Xposed 入口与系统钩子）、 pip （画中画工具）、 ucar （UCar 车机地图服务）、 notouch （镜像/投屏）、 auto （开机与系统 UI 插件）。

 2 Xposed 模块入口与包名分发
 入口类是 com.leting.xposed.xphook ，实现 IXposedHookLoadPackage 接口，核心方法 handleLoadPackage(LoadPackageParam) 按 packageName 分发到不同钩子。
 com.miui.carlink / com.baidu.carlife.xiaomi / com.samsung.android.carlink — 记录 CarLink 加载日志。
 com.android.systemui — 调用 hookAmapPip(classLoader) ，hook SystemUI 的 PiP 尺寸算法。
 com.netease.cloudmusic.iot — 调用 hookNeteasePip() ，为网易音乐 Iot 版的 startActivity 注入目标 displayId。
 com.autonavi.minimap — 优先加载 com.leting.carplay.AmapNaviHook 调用其 init(LoadPackageParam) ；找不到则走 hookAmapNaviInline(classLoader) 内联 hook。
 // xphook.smali — handleLoadPackage 分发逻辑（节选） 
 if -eq pkgName, "com.android.systemui" -> hookAmapPip(classLoader) 
 if -eq pkgName, "com.netease.cloudmusic.iot" -> hookNeteasePip() 
 if -eq pkgName, "com.autonavi.minimap" :
 try AmapNaviHook.init(classLoader)
 catch -> hookAmapNaviInline(classLoader) 
 复刻要点
 LSPosed API 102 模块声明（ xposedmodule / xposedminversion / xposed_scope ）是整套 hook 能被 LSPosed 激活的前提；handleLoadPackage 的包名分发决定每个钩子的生效目标。

 3.5 辅助解析方法
 processWy4Data(String road, String next, String desc, int iconType) — 校验 iconType ∈ [2,66] 则写 sIconType ，解析道路/描述并回填缓存，随后触发广播。
 parseDistance(String) — 把高德文案（"剩余 / 约 / 全程 / 预计 / 还有 / 公\u91cc / 米"等）清洗成整数， parseFloat 后转 int（含失败回退 0）。
 extractFromNotification(Notification) — 从高德通知 extras 提取导航文本与图标位图（写入 sIconBitmapBytes ）。
 extractPoiInfo(Object, boolean) / extractRoadName(String) / getIntFieldSafe — 反射安全取字段。
 isNaviActive() — 对外暴露导航活跃状态。
 复刻要点：为何有多路 hook
 高德不同版本/不同 UI 层（JNI 模型、AJX 路由模块、通知）都可能携带导航数据，故用多 hook 兜底。任意一处在句柄回调里调用同一套 写缓存→broadcastNaviUpdate 流程，保证数据不丢。

 4.1 CarPlayHelper$4 接收端
 CarPlayHelper$4 实现 BroadcastReceiver.onReceive ，从 NAVI_UPDATE 读取全部字段写入 CarPlayHelper 静态缓存（ sCachedIconType 、 sCachedCurStepDist 、 sCachedCurRoad 等 9 个 + sCachedLastNaviUpdate 时间戳），并判断导航活跃（iconType>0 且 curStepDist>0 且 remainDist>0 → sNaviActive=true ），随后调用 NaviCardView.updateNaviData(...) 与 setArrowBitmap(bytes) 驱动 UI。

 6 画中画（PiP）实现
 画中画分两层：一层是 修改 SystemUI 的 PiP 窗口尺寸算法 （AmapPipHook，hook com.android.wm.shell.pip ），让进入 PiP 的高德导航窗口放大到目标的 60% 屏幕短边占比；另一层是 跨显示器启动与任务迁移 （NetEase 的 displayId 注入 + TaskMover 反射移任务），让应用在指定屏幕以 PiP 形态显示。
 6.1 AmapPipHook：hook SystemUI PiP 尺寸
 PiP 尺寸相关 hook（目标类 com.android.wm.shell.pip） 
 Hook | 目标类/方法 | 作用 | 
 hookSetBoundsStateForEntry | PipBoundsState.setBoundsStateForEntry(ComponentName, ...) | before：把 ComponentName 的包名写入 CurrentPip.sPackageName | 
 hookGetSizeForAspectRatio(Size) | PipBoundsAlgorithm.getSizeForAspectRatio | after：是 Amap PiP 则 scaleToTarget(result, shortDim) 并 setResult | 
 hookAdjustSizeToAspectRatio | PipBoundsAlgorithm.adjustSizeToAspectRatio(Size) | 同上，缩放返回值 | 
 hookTransformBoundsToAspectRatio | PipBoundsAlgorithm.transformBoundsToAspectRatio(Rect) | before：记录输入 Rect 以便定位 | 
 判断是否目标 PiP： CurrentPip.isAmap() 比对包名 com.autonavi.minimap ；未命中时经 getObjectField("mPipBoundsState") → getLastPipComponentName() 回查。尺寸计算用 getDisplayShort() （从 mPipBoundsState.getDisplayLayout() 读显示短边）， scaleToTarget 用常量 TARGET_SIZE_PERCENT = 0.6f 缩放。 CurrentPip 是静态 volatile sPackageName 的辅助类。
 6.2 NetEasePip：跨显示器启动注入
 hook 网易音乐 IoT 版的 6 个加载体： Activity/Context.startActivity 与 startActivityForResult 。在 each call 里调用 injectNeteaseDisplayId ：取当前 Activity 的 Display.getDisplayId() ，若 shouldPinNeteaseIntent(intent) 命中，则用 ActivityOptions.makeBasic().setLaunchDisplayId(displayId).toBundle() 注入，让目标 activity 在指定显示器启动。
 shouldPinNeteaseIntent 的命中规则：无 Component、类名含 "Iot" / "Player" 、属于 NETEASE_PINNED_ACTIVITIES 白名单（如 IotPlayerActivity、IotRadioPlayerActivity、IotSceneRadioPlayerActivity、IotPodcastPlayerActivity、IotRedirectActivity、IotLoginActivity、IotDeveloperActivity），或以 com.netease.cloudmusic. 开头。

 6.4 进入画中画的常规面（非 hook）
 除 hook SystemUI 尺寸外，Android 进入 PiP 的标准做法是 Activity.enterPictureInPictureMode() + Manifest 声明 android:supportsPictureInPicture 。本 APK 的 PiP 主路径是 Xposed 侧改系统，宿主侧配合 PipAnchorActivity 与 TaskMover ，把投屏/网易 IoT 窗口落到指定显示的 PiP。
 7 悬浮投屏宿主 CarPlayOverlayService
 CarPlayOverlayService （前台服务， foregroundServiceType="specialUse" ）是悬浮层宿主，用 WindowManager.addView 创建两套浮窗： 侧边栏 mSidebarView 与 导航面板 mNavPanelView 。
 监听 7 个导航/通信广播： NAVI_UPDATE 、 NAVI_STATE 、 HOME_COMPANY 、 UCAR_NAVI_DATA 、 UCAR_NAV_STATUS 、 COMMUTER_ADDR 、 UCAR_NAVI_REMOVE 。
 createNavPanel() ： WindowManager.LayoutParams 在 SDK≥26 用 type= 0x7f6 （TYPE_APPLICATION_OVERLAY）否则 0x7d6 （TYPE_PHONE）；高= (屏高-14dp)×0.59 、宽= mNavPanelWidth=屏宽×0.15 、gravity=0x35(右上)、y=10dp；内部 buildNavContent() 建导航卡片、 buildMusicContent() 建音乐面板。侧边栏宽= 0.13×屏宽 。
 createOverlays()/removeOverlays() ：以 mOverlaysAdded 标志防止重复；移除侧边栏与导航面板。
 偏好存储在 carplay_prefs SharedPreferences：家/公司地址、常驻侧边栏应用（最多 8 个）、开关 carplay_enabled 等。

 8.4 已知坑与建议
 setContentView 类型 ：原 APK 曾因把 DataBinding 对象当 View 传给 setContentView 导致 ClassCastException 闪退。新工程务必 binding.getRoot() 后再传 View。

 29 已知分析缺口、验证方法与风险
 诚实补充逆向中仅靠静态无法确认的点，以及上线后必须做的验证，避免重写踩到同样的不确定性。
 29.1 静态分析无法确认的项
 高德 JNI 行为 ： RouteNaviInfo/CurrentNaviInfo 真实填充时机依赖高德 native 层，重写后需真机验证实际触发频率。
 SystemUI 版本差异 ：PiP 的 PipBoundsAlgorithm.getSizeForAspectRatio 、 PipBoundsState.setBoundsStateForEntry 方法签名随 Android 12/13/14 差异大，本文为反编译目标机的调用，需按目标 SDK 适配。
 混淆 R 常量 ：R 经 R8 混淆（binding 类 g1.a 、id 0x7f090077 等），重写建议用规范 ViewBinding + 字符串资源名，不依赖混淆 id。
 悬浮窗授权 ：依赖用户手动授予 SYSTEM_ALERT_WINDOW ，无法代码规避。
 29.2 发布前必做的验证清单
 导航链路 ：真机进高德导航， NAVI_UPDATE 持续刷新、箭头/距离/方向/路名正确（§25 契约逐字段核对）。
 状态切换 ：开始/结束导航时 NAVI_STATE 的 active 正确翻转，卡片回空闲态。
 家/公司 ：设置后 HOME_COMPANY 带出坐标，点击卡片拉起 amapuri （§14）。
 PiP ：按 Home 后高德进 PiP 且缩放到 60% 短边、落到目标屏（§11）。
 开机自启 ：重启后桌面落到 display 0（§21）。
 权限 ：悬浮窗 + 无障碍 + 投屏三项授权齐全后再测全流程。
 29.3 root 与签名风险
 原包需 root + LSPosed（签名一致），SystemUI hook 在 OEM 定制 ROM 上可能被阉割；投屏 MediaProjection 在新版 Android 需前台服务 + 用户确认弹窗，全自动化需系统授权。以上为风险项，发布前应在目标车型/ROM 上回归验证。
